# 나의 위키 — 운영 스키마

이 파일은 LLM(Claude)이 이 위키를 어떻게 관리하는지 정한 규칙이다.
안드레이 카르파시의 "LLM Wiki" 아이디어를 바탕으로 한다:
원본 자료를 질의 때마다 다시 뒤지는 대신, LLM이 자료를 읽을 때마다 **영구적이고 서로 연결된 위키를 조금씩 쌓아 간다.**

- **사용자**: 원본 자료를 고르고, 질문하고, 방향을 정한다.
- **LLM**: 요약, 페이지 작성, 상호 링크, 색인·로그 관리 등 나머지 모든 장부 정리를 맡는다.

이 스키마는 사용자와 함께 계속 고쳐 나간다. 작업 방식이 바뀌면 이 파일도 갱신한다.

---

## 1. 언어와 문체

- 모든 위키 페이지는 **한국어**로 작성한다.
- 백과사전 문체(평서형 "~이다", "~한다")를 쓴다. 대화체·존댓말은 쓰지 않는다.
- 고유명사와 전문 용어는 처음 나올 때 원어를 괄호로 병기한다. 예: 검색 증강 생성(Retrieval-Augmented Generation, RAG)
- 원본이 외국어여도 위키 페이지는 한국어로 요약한다. 꼭 필요한 짧은 원문 표현만 따옴표로 인용한다.
- 사용자와의 대화도 한국어로 한다.

## 2. 디렉터리 구조

```
mywiki/
├── CLAUDE.md            ← 이 파일 (스키마)
├── README.md            ← 사용자용 안내서
├── raw/                 ← 원본 자료 (불변, LLM은 읽기만 함)
│   ├── notes/           ← 내가 쓴 메모, 강의 필기 (예: 나에게 보낸 메일)
│   ├── articles/        ← 웹 글, 뉴스레터에서 골라 둔 글
│   ├── email/           ← 메일에서 모은 자료
│   └── assets/          ← 원본에 딸린 이미지 등 첨부 파일
└── wiki/                ← LLM이 작성·관리하는 위키
    ├── index.md         ← 전체 페이지 목록 (질의 시 가장 먼저 읽음)
    ├── log.md           ← 작업 기록 (추가만 함)
    ├── 개요.md           ← 위키 전체를 조망하는 대문 페이지 (주제 지도)
    ├── topics/          ← 주제 허브: 큰 관심 영역별 출발점 페이지
    ├── sources/         ← 원본 자료 하나당 요약 페이지 하나
    ├── entities/        ← 개체: 서비스, 기관, 강의, 인물, 작품 등
    ├── concepts/        ← 개념: 개발 개념, 아이디어, 이론, 기법
    ├── projects/        ← 직접 만드는 것 (실습 앱 등)
    └── analyses/        ← 질의 결과, 비교표, 종합 분석
```

### 주제 영역
현재 주제 허브는 다섯 개다 (`wiki/topics/`). 새 페이지는 반드시 하나 이상의 허브에서 링크되게 한다.

| 허브 | 범위 | 비중 |
|---|---|---|
| 바이브코딩 | 강의 노트, 개발 개념, 개발 도구, 실습 프로젝트 | 중심 |
| AI 도구 | 써 본 AI 서비스 후기, AI 업계 소식 | 높음 |
| 업무 | 한국고용정보원, 고용24 앱 | 중간 |
| 생활과 취미 | 듀오링고, DAY6, 소비·여행 정보 | 중간 |
| 경제와 시사 | 뉴스레터에서 골라 둔 경제·사회 소식 | 낮음 |

- 뉴스레터(뉴닉, 어피티 등)는 모든 호를 넣지 않는다. 사용자가 고른 글만 수집한다.
- 강의 필기는 `concepts/`에 개념을 뽑아내고, 수업 날짜별 페이지(`sources/`)는 개념으로 링크한다.
- 업무 자료는 내부 정보가 섞일 수 있으니, 수집 전에 민감한 내용이 있으면 사용자에게 알린다.
- 주제가 새로 커지면(관련 페이지 10개 이상) 허브 추가를 사용자에게 제안한다.

### 절대 규칙
- `raw/` 안의 파일은 **절대 수정·삭제·이동하지 않는다.** 원본은 진실의 근거다.
- `wiki/` 는 LLM이 전적으로 책임진다. 사용자가 직접 고친 내용이 있으면 존중하고 덮어쓰지 않는다.

## 3. 페이지 규칙

### 파일 이름
- 페이지 제목을 그대로 파일 이름으로 쓴다. 예: `wiki/concepts/검색 증강 생성.md`
- 한국어 이름을 우선한다. 한국어 이름이 어색한 고유명사는 통용되는 표기를 쓴다. 예: `wiki/entities/OpenAI.md`
- `sources/` 페이지는 원본 파일 이름(확장자 제외)과 같게 해서 짝을 쉽게 찾게 한다.
- 같은 대상의 페이지를 두 개 만들지 않는다. 새로 만들기 전에 `index.md`와 파일 목록을 확인한다.

### 머리말(frontmatter)
모든 페이지 맨 위에 YAML 머리말을 단다. 키는 Obsidian Dataview 호환을 위해 영어, 값은 한국어로 쓴다.

```yaml
---
title: 검색 증강 생성
type: concept          # source | entity | concept | project | topic | analysis | overview
tags: [인공지능, 검색]
aliases: [RAG]         # 다른 이름 (Obsidian 링크 검색용)
created: 2026-11-13
updated: 2026-11-13
sources: 2             # 이 페이지가 근거로 삼는 출처 수
---
```

`type: source` 페이지는 다음을 추가한다:
```yaml
raw: raw/파일이름.md    # 원본 경로 (원본이 URL뿐이면 생략)
url: https://...       # 원본 주소 (있으면)
author: 저자
published: 2026-01-01  # 원본 발행일 (알면)
```

### 링크
- 페이지끼리는 Obsidian 위키링크 `[[페이지 제목]]` 로 연결한다. 표시 이름이 다르면 `[[페이지 제목|표시할 글]]`.
- 다른 페이지가 있는 개체·개념이 본문에 나오면 **처음 등장할 때** 링크를 건다.
- 아직 페이지가 없지만 중요한 대상도 링크를 걸어 둔다(빨간 링크). 점검(lint) 때 페이지를 만들 후보가 된다.

### 출처 표시
- 사실 주장에는 근거가 된 출처 페이지를 붙인다. 형식: 문장 끝에 `([[출처 페이지 제목]])`
- 출처 없이 LLM이 추론하거나 덧붙인 내용은 `> [!note] 해석` 콜아웃 안에 따로 적어 사실과 구분한다.

### 상충과 갱신
- 새 자료가 기존 내용과 어긋나면 **조용히 덮어쓰지 않는다.** 두 주장을 모두 남기고 표시한다:
  ```
  > [!warning] 상충
  > [[출처 A]]는 X라고 하나, [[출처 B]]는 Y라고 한다.
  ```
- 더 새로운 자료가 옛 주장을 대체하면, 옛 주장을 `~~취소선~~` 또는 "이전에는 ~로 알려졌다" 형식으로 남기고 새 내용을 적는다.
- 페이지가 길어지면 단락을 덧붙이기보다 **요약을 다시 쓴다.** 덧붙이기만 하면 위키가 지저분해진다.

### 페이지 유형별 뼈대

**sources (출처 요약)**
```
# 제목
한두 문장 요약.
## 핵심 내용
## 주요 주장·데이터
## 등장하는 개체와 개념   ← [[링크]] 목록
## 나의 메모              ← 사용자와 논의한 내용, 사용자의 의견
```

**entities / concepts**
```
# 제목
정의 한두 문장 (백과사전 첫 문단처럼).
## 개요
## (주제에 맞는 소제목들)
## 관련 항목            ← [[링크]] 목록
## 출처                ← 이 페이지가 인용한 [[출처 페이지]] 목록
```

**topics (주제 허브)**
```
# 주제 이름
이 주제에서 무엇을 모으는지 한두 문장.
## (하위 묶음별 소제목)   ← 각 항목은 [[링크]] — 한 줄 설명
## 더 채울 것            ← 넣으면 좋을 자료, 열린 질문
## 관련 주제
## 출처
```

**projects (프로젝트)**
```
# 프로젝트 이름
무엇을 만드는지 한두 문장.
## 현재 상태              ← 된 것 / 안 된 것
## 쓰는 기술              ← [[개념]], [[도구]] 링크
## 진행 기록              ← 날짜별 한 줄, 근거 출처 링크
## 출처
```

**analyses (분석·질의 결과)**
```
# 제목 (질문 형태도 가능)
결론 요약.
## 근거
## 남은 질문
## 출처
```

## 4. 작업 흐름

### 4.1 수집 (Ingest) — 새 자료 넣기
사용자가 `raw/`에 자료를 넣고 "수집해 줘"(또는 `/ingest 파일`)라고 하면:

1. 원본을 끝까지 읽는다. 이미지가 있으면 본문을 먼저 읽고, 필요한 이미지는 따로 열어 본다.
2. 사용자에게 **핵심 요점 3~5개**를 한국어로 짧게 말하고, 특히 강조할 점이나 관점이 있는지 묻는다. (사용자가 "알아서 해"라고 하면 바로 진행)
3. `wiki/sources/`에 출처 요약 페이지를 만든다.
4. 자료에 나오는 개체·개념마다:
   - 페이지가 있으면 → 새 정보를 반영해 **고쳐 쓴다** (확장 우선, 새로 만드는 건 그다음).
   - 없고 중요하면 → 새 페이지를 만든다.
   - 기존 내용과 어긋나면 → 상충 표시를 한다.
5. 필요하면 `wiki/개요.md`를 갱신한다.
6. `wiki/index.md`를 갱신한다.
7. `wiki/log.md`에 기록을 추가한다.
8. 사용자에게 무엇을 만들고 고쳤는지 목록으로 보고한다.

자료 하나가 10~15개 페이지를 건드리는 것은 정상이다.
여러 자료를 한꺼번에 넣으라고 하면 하나씩 차례로 처리하되, 2번 단계는 생략하고 마지막에 한 번에 보고한다.

### 4.2 질의 (Query) — 위키에 묻기
사용자가 질문하면:

1. `wiki/index.md`를 먼저 읽고 관련 페이지를 고른다.
2. 해당 페이지들을 읽고, 필요하면 링크를 따라 더 들어간다. 위키로 부족하면 `raw/` 원본을 확인한다.
3. 출처 링크를 붙여 한국어로 답한다.
4. 답이 다시 쓸 만한 가치가 있으면(비교, 종합, 새 통찰) `wiki/analyses/`에 페이지로 저장할지 사용자에게 제안한다. 저장하면 index와 log도 갱신한다.

답은 형식이 자유롭다: 글, 비교표, Marp 슬라이드, 차트 등.

### 4.3 점검 (Lint) — 위키 건강 검진
사용자가 "점검해 줘"(또는 `/lint`)라고 하면 다음을 찾아 보고한다:

- 페이지 사이의 **모순**
- 새 자료로 **낡아진 주장**
- **고아 페이지**: 아무 데서도 링크되지 않은 페이지
- **빨간 링크**: 링크는 있지만 페이지가 없는 대상 (자주 언급되면 페이지 생성 후보)
- **빠진 상호 링크**: 서로 언급하면서 링크가 없는 페이지
- **index 누락**: index.md에 없는 페이지, 또는 없는 페이지를 가리키는 index 항목
- **머리말 오류**: 빠진 키, 틀린 type, 갱신 안 된 updated
- **지식의 빈틈**: 더 찾아볼 만한 질문과 자료 제안

보고한 뒤, 사용자가 동의하면 고친다. 점검도 log에 남긴다.

## 5. index.md 형식

- 범주별로 나눈다: 개요 / 주제 / 출처 / 개체 / 개념 / 프로젝트 / 분석
- 각 항목은 한 줄: `- [[페이지 제목]] — 한 줄 요약 (출처 N)`
- 출처 항목은 날짜를 앞에 붙인다: `- [[제목]] — 한 줄 요약 · 2026-11-13 수집`
- 범주 안에서는 가나다순으로 정렬한다.
- 맨 위에 전체 페이지 수와 마지막 갱신일을 적는다.

## 6. log.md 형식

- **추가만 한다.** 예전 기록은 고치지 않는다. 새 기록은 맨 아래에 붙인다.
- 모든 기록은 같은 머리글 형식으로 시작한다 (grep으로 파싱 가능하게):
  ```
  ## [YYYY-MM-DD] 종류 | 제목
  ```
  종류: `setup`(설정) · `ingest`(수집) · `query`(질의) · `lint`(점검) · `schema`(스키마 변경)
- 머리글 아래에 만든 페이지, 고친 페이지, 메모를 짧게 적는다.
- 최근 기록 5개 보기: `grep "^## \[" wiki/log.md | tail -5`

## 7. 기타

- 작업을 시작할 때 `wiki/log.md`의 최근 기록을 훑어 맥락을 파악한다.
- 날짜는 항상 `YYYY-MM-DD` 형식.
- 이 위키는 git 저장소다. 사용자가 요청할 때만 커밋한다.
- 위키가 커져서 index.md만으로 찾기 어려워지면(수백 페이지 이상), 검색 도구(예: qmd) 도입을 사용자에게 제안한다.
